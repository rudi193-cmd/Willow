# Service migration — systemd user units after the greenfield reset

**Status:** decision record · operator guide · **2026-08-10**
**Completes:** the `~/.config/systemd/user/*.service` line of the path-migration
checklist in [`LOCAL_GITHUB_LAYOUT.md`](LOCAL_GITHUB_LAYOUT.md), and step 7 of
the wire-up order in `~/github/GREENFIELD-FOR-CLAUDE.md`.
**Scope:** decides keep / port / drop for every unit the reset stranded. It does
not change any unit; nothing here has been applied.

---

## Why most of them died

The units split cleanly along one line, and it is not the one the checklist
implies:

- **Code under `~/.willow` survived.** `~/.willow` is a symlink into
  `willow-memory/.willow`, so anything executing from there followed the move
  without edits. `sentinel-watchdog` is the proof — it runs
  `%h/.willow/fleet-dispatch/sentinel_watchdog.py`, and it is still firing on
  its timer today.
- **Code under `willow-2.0` did not.** That repo is tier F: archived by intent,
  listed under *"Do not use"* in the greenfield handoff, and **absent from this
  machine entirely** — not in `~/github/archive/`, not in
  `~/github-archive-greenfield-2026-08-10/`, nowhere. Only a single WIP branch
  bundle remains.

So eleven of thirteen are not misconfigured. Their code no longer exists, and
"rewrite the ExecStart path" has nowhere to point. This is a decommissioning
decision, not a repointing exercise.

---

## The standard to migrate *to*

`willow_mcp/worker_service.py` defines it, and its opening doctrine is the part
that matters most:

> Install and uninstall only manage unit files and daemon-reload. **They never
> start, stop, enable, or disable a live service.**

A unit meeting willow-mcp standards is therefore:

| property | why |
|---|---|
| **Generated by the product** (`willow-mcp <thing>-service install`), not hand-written | a hand-written unit is a second source of truth for paths that already live in `$WILLOW_HOME` |
| **Paths derived** from `$WILLOW_HOME` / `$WILLOW_STORE_ROOT`; python from `sys.executable` | this is exactly why three `willow-mcp-*` units already work post-move and thirteen do not |
| **Policy pinned explicitly** where a silent fallback would break it | `worker_service` writes the Kart sandbox config as a literal `Environment=` line, because a worker that cannot resolve fleet policy falls back to kartikeya's vendored default and fails *every* task |
| **Runtime state left to the operator** | the installer never enables or starts; that all four `willow-mcp-*` units sit `disabled` is deliberate, not an oversight |

### Most of these should not be units at all

The old fleet made every job a daemon. willow-mcp's model is **one worker, many
queued tasks** — `task_submit` into a fast or batch lane. Seven of the thirteen
were periodic work, not long-lived listeners, and under this model the bespoke
unit disappears:

```
systemd .timer  →  willow-mcp task_submit (lane=batch)  →  worker executes
```

The job gets Kart's sandboxing, the receipt trail, and the permission gate for
free, and the thing systemd owns shrinks to a trigger.

**Caveat:** Kart has no recurring-task primitive — the only interval logic in
the tree is `soil_heartbeat.interval_sec_for`. A `.timer` is still required as
the trigger. What changes is that it calls `task_submit` instead of executing
bespoke code.

## The decisions

### Keep — 1

| unit | action |
|---|---|
| `gitsync` | Two env lines. `~/.local/share/gitsync/gitsync-loop.py` is alive and **pure stdlib** — no willow imports at all. Point `WILLOW_REPO_ROOT` at the org layout and drop the `PYTHONPATH=…/willow-2.0` line; the `Documentation=` URL is cosmetic. |

### Drop — 1 superseded, 4 blocked

| unit | action |
|---|---|
| `orin-worker` | **Superseded.** Batch processing is `willow-mcp-worker-batch`, which exists and is generated by `worker-service`. Its `agents.orin` package is gone with willow-2.0. |
| `grove-mcp`, `willow-grove-listen` | **Blocked, not portable.** willow-mcp contains *no grove code*, and `safe-app-willow-grove` is not cloned on this machine. These wait on a repo decision, not a migration. |
| `willow-w8-census`, `willow-wce` | **No successor exists.** Both were `willow.sh` subcommands (`w8-census`, `wce`). Rebuilding them is new feature work; nothing in willow-mcp covers a census or continuity-eval. |

### Port — 4

| unit | target | notes |
|---|---|---|
| `kb-snapshot-refresh` | Kart batch task | **Do this one first, for a reason unrelated to migration:** its timer is *active* and its service fails every run (`status=203/EXEC`). The `kb_*` tools (`kb_ingest`, `kb_promote`, `kb_journal`, `kb_at`) cover the capability; only the bespoke `export_kb_snapshot.py` wrapper is gone. **Disable the timer now**, port later. |
| `hook-wiring-audit` | willow-mcp tool or batch task | Natural fit — willow-mcp already owns project wiring (`project_wiring.py`, `mcp_projects.py`), so auditing it belongs there rather than in a standalone script. |
| `nest-watcher` | `*-service` installer | The strongest listener candidate: `nest_digest`, `nest_intake_file`, `nest_intake_flags` already exist. What is missing is only the watch loop. Build it the `worker_service` way. |
| `drop-server` | fold into the above, or drop | HTTPS upload into `~/Desktop/Nest`; `nest_intake_file` covers the ingest half. Worth asking whether the upload endpoint is still wanted before rebuilding it. |

### Undecided — 2, operator call

| unit | question |
|---|---|
| `willow-metabolic` | The Norn scheduler. willow-mcp has **no scheduler primitive**, and the "one worker, many tasks" model may make it unnecessary — or may need it back once several timers exist. |
| `stuck-loop-watch` | A watchmen-class detector; no watchmen concept in willow-mcp. Note `sentinel_watchdog.py` (a sibling of the same family) lives under `~/.willow/fleet-dispatch/` and **survived** — so the family's home is already the durable one. |

## Order of operations

1. **`systemctl --user disable --now kb-snapshot-refresh.timer`** — stops a
   daily failure that is unrelated to whatever is decided below.
2. **`gitsync`** — two lines, and it works again.
3. **Retire** the superseded and blocked units as one batch, so the list stops
   reading as thirteen pending problems.
4. **Port** the four, in the order above.
5. **Fix `willow-mcp-worker@.service`** — it points at `willow-mcp/.venv`, a
   per-repo venv that does not exist; the fleet venv is `$WILLOW_HOME/venvs/`.
   Its two siblings are already correct.

Enabling anything is a separate act, and Postgres (step 1 of the greenfield
wire-up) has not been done — the workers take `--require-postgres`.
